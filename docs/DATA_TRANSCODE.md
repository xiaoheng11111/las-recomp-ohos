# 游戏数据转码：方法与边界（DATA_TRANSCODE）

> 原则：**方法可以开源，数据只能自用。**
> 重编译/转码不改变版权归属——格式变了，内容还是原游戏；转码后的数据包/成品不要发布。

本文只讲“拿到你自己合法 dump 的 `exefs/romfs` 之后，怎么做转码”，不提供提取/解密工具，也不包含任何游戏数据。

---

## 1. 视频转码（已在本项目实际使用过）

目标：把 Switch 的 VP9/WebM 过场换成目标平台更容易解码的编码（例如 H.264），或配合硬解。

### 1.1 定位视频文件

- 用你自己的 RomFS 工具导出/查看文件表，视频通常在：
  `bin/movies/<游戏>/title_*.webm`（不同游戏路径不同）；
- 记录每个视频的：**RomFS 内偏移、原始字节数**。

### 1.2 转码命令示例（VP9 → H.264/AAC）

```bash
ffmpeg -i in.webm -map 0:v:0 -map 0:a:0 \
  -c:v libx264 -preset slow -crf 20 -profile:v high -level:v 4.0 \
  -pix_fmt yuv420p -g 60 -keyint_min 30 -sc_threshold 0 \
  -c:a aac -b:a 128k -ar 48000 -ac 2 -movflags +faststart out.mp4
```

容器选择建议：
- 原文件是 WebM/Matroska 时，**优先 Matroska(.mkv) 装 H.264+AAC/Opus**，最贴近原来的解封装路径；
- MP4 也能用（FFmpeg 按内容识别容器），但在“自定义 IO 读取 romfs 区间”的场景下，曾遇到过第二段动画 `avformat_open_input` 崩溃的案例，所以能 MKV 就 MKV。

### 1.3 原位替换（保持 RomFS 大小不变）

如果不想改 RomFS 元数据：
1. 让转码结果**不大于**原文件（通过 CRF/码率控制）；
2. 在文件尾部**补零**到原始字节数；
3. 按原偏移原位写回；
4. RomFS 的文件大小/偏移不变，校验与索引都不受影响（尾部零字节不会被播放器使用）。

### 1.4 或者用 Mod Overlay

- 把转码后的文件放在 `mods/<名字>/romfs/<原相对路径>`（LayeredFS 思路），运行时优先读 mod 文件；
- 不动 `romfs.bin`，最安全、可回滚。

### 1.5 视频硬解

- H.264 / HEVC：HarmonyOS AVCodec 支持硬解，可用 `h264_ohcodec` / `hevc_ohcodec`；
- VP9：设备通常不提供硬解，只能软解；
- 注意收益：**视频硬解只影响动画阶段**；如果掉帧发生在游戏场景，硬解没有帮助。

## 2. 纹理转码（思路，不提供工具）

Switch（Tegra）纹理可能是 BCn / ASTC 等格式，并带 Tegra 专用 swizzle。部分移动 GPU（如 Maleoon）不支持 BC，只能在 CPU 上软解后上传，这就是移植层的一笔 CPU/带宽开销。

可尝试的方向：
1. 用你自己的资源工具解包纹理；
2. 转成目标 GPU 原生支持的格式（ASTC / ETC2 / 线性 RGBA8）；
3. 重打包回 romfs（或走 mod overlay）。

注意：
- 必须保持 mip、sRGB、尺寸/对齐、引用关系正确；
- 有的游戏会校验资源，改错会花屏/崩溃；
- 收益是**减少 BC 软解/带宽/deswizzle**，**不会减少 draw call**；
- 转换后的资源仍属游戏版权内容，只能自用。

---

## 3. 模型 / 场景 / 绘制结构

- 这些**不能靠数据转码解决**；
- 户外/植被掉帧的主因是 **draw call 数量**（场景结构 + 渲染提交），属于运行时合批/实例化的范畴。

---

## 4. 先判断瓶颈，再决定转什么

在游戏里打开「帧时间诊断」（`LARECOMP_VK_PROF`），抓 `[hitch]`：

- `GPU waits` 高 → GPU/带宽瓶颈：转纹理（ASTC/ETC2）、视频硬解、降分辨率可能有帮助；
- `backend exec` 高、`GPU waits` 低 → CPU 瓶颈（draw call/上传/翻译）：优先合批、纹理缓存/上传优化，转数据帮助有限。

---

## 5. 合规边界

- 转码后的视频/纹理/数据包：**只能自己用**，不要上传 GitHub、网盘或任何公开渠道；
- 可以开源的是：转码方法（本文）、运行时/启动器代码、构建脚本、不绑定游戏数据的工具；
- 不要发布 `liblasgame.so`、`romfs.bin`、`exefs/`、成品 HAP/APK（含游戏内容）。

---

## 6. 经验总结（本项目）

- 视频从 VP9 转 H.264 后，动画并没有明显变快——说明当时瓶颈在**呈现/纹理上传**，不是解码；
- 这说明“先转数据”不是万能药：先 `[hitch]` 定位，再决定转视频、转纹理，还是做合批。
